## 先行审查结论与采用的简化

总体分层和稳定 ID 方案合理。本阶段只需要法器和敌人，合并为一个 `ContentRegistry`，不创建空的 Character/Buff Registry。`BattleSimulation` 同时承担当前极小的 ItemSystem/CombatSystem 编排工作，伤害保留独立 `EffectSystem` 接口。待实际职责增多再拆分，避免空转发层。

不建立完整 Trigger/Condition 框架；配置只允许 `on_activate`，未知触发或效果明确拒绝，不能静默忽略。未实现任何 MOD 目录扫描、代码执行、存档和平台集成。官方 JSON 经过统一注册入口，为以后外部数据复用这一入口保留空间。

事件队列采用小型稳定最小堆，入队/出队 O(log n)。时间采用整数微秒，输入 delta 的微小余数留在时钟中；模拟无需固定步长，直接处理目标时刻之前的事件。不同帧长下，每次攻击都发生在同样的游戏时刻。

只有全局模拟入口每帧推进一次。8× 在相同真实时间内自然要处理更多到期事件，但不让每件道具、每个 UI 节点扫描或重复跑八遍。UI 的刷新率和游戏速度分开。V0.1 没有为极端事件爆炸建立预算/欠账系统，未来连锁效果必须加入循环限制与预算，不能简单丢弃到期事件。

胜利后清空事件队列、不再伤害，时钟继续推进；保留 `defeated_at_usec` 区分世界时间与战斗完成时间。暂停冻结游戏时间。重新开始生成新的模拟对象，不重读 JSON，默认恢复 1× 并开始运行。

Registry 中的 ItemData 按约定只读；敌人定义返回深拷贝。当前只实现一个实例，实例包含稳定内容 ID 和实例 ID，未将静态配置复制进可存档状态。以后多实例系统需进一步封装定义的不可变性。

UI 采用原生 Control/Container，无外部框架。字体使用系统 CJK 字体解决原型中文显示。布局与字体大小以设计分辨率定义，面板位置由容器计算。表现层暂时是有长度上限的战斗记录，之后可订阅同一批事件增加音效或动画。

## 验收边界

必须通过 JSON 加载、脚本解析、主场景启动，以及 1/2/4/8× 等价性测试。只测 100 HP 木桩容易把后续事件丢失掩盖掉，因此另外用 10000 HP 的测试实例验证 60 秒内 20 次攻击；测试替身不改变正式内容。

还验证 30/60/144 FPS、同时间事件稳定顺序、长帧补算、精确边界、暂停中切速、恢复、重开、死亡和过量伤害，以及按钮到状态再到 UI 的完整联动。渲染检查使用真实 Mobile / D3D12，在 16:9、16:10、超宽与最小窗口生成画面。

导出 Windows 包不在本阶段要求中。以后导出时需显式包含 `data/**/*.json`，并在导出产物上重跑内容加载验收，不能仅凭编辑器内正常就认为打包成功。
