**有几处需要修正和补齐，但这次不需要再从头重写。**新版04已经把你刚确认的攻击类型、武器器型、防具元素和换装规则放到了正确的位置。现在的问题主要在**不同规格之间的衔接**，尤其是消耗品、伤害包、来源身份，以及迁移清单的操作范围。

这次我审的是**新版两批正文＋独立迁移清单**，并对照了已上传的01、02词典；不是在审查尚未提供的04 Excel。

先明确：**你已经确认的四攻击类型、法术型效率、九种武器器型、盾反击为钝击、防具元素聚合、护甲换装截上限、不可旋转、无射程、无耐久，这轮都不重新打开讨论。**

下面是建议交给Codex合并的审校内容。

# 一、最先要改：消耗品“会被消耗”，不等于“不在阵盘上”

新版第2批的最终矩阵，把丹药、符箓、暗器的“持续上阵”统一填成了“否”。**这个表述不准确，应撤回。**

它混淆了两件事：

> **物品怎样参与战斗。**  
> **物品发动时是否消耗数量。**

一叠符箓完全可以先放在战斗阵盘里，占据格子，等待CD并接受相应控制；每次发动再消耗其中一张。

不能因为符箓是消耗品，就自动推导出：

> 不占格、不需要上阵、存在独立快捷栏，或者可以随时从储物袋发动。

这些都会改变现有战斗布局，而不是单纯整理规格。

## 建议改成两个独立字段

| 规格 | 回答的问题 |
|---|---|
| **战斗承载方式** | 放在阵盘、通过已确认的其他战斗入口使用，还是只能非战斗使用？ |
| **消耗模型** | 发动是否消耗实体数量、内部次数或其他资源？ |

对应地，六类矩阵里的“持续上阵”一栏应改为：

> **按实际战斗承载方式填写，不按消耗品身份直接判否。**

对于放入阵盘的丹药、符箓和暗器，尺寸、位置、战斗实例及运行状态仍然需要记录。

### `Use_Context`也要一起调整

上一版把：

> `BATTLE_BOARD`、`BATTLE_CONSUMABLE`、`TRAINING`、`MULTI_CONTEXT`

放在同一个枚举里，实际上混合了**容器、使用方式和环境**。

建议拆为：

> **允许使用环境**：战斗、修炼、探索等，可以有多个。  
> **使用入口／承载方式**：阵盘、非战斗直接使用等，引用已确认的入口。

`MULTI_CONTEXT`不用成为一个独立值。它不能告诉系统究竟允许哪几个场景。

# 二、消耗品的库存、上阵数量和CD关系还没有完整定义

上一版已经区分了模板、库存堆叠、战斗实例，这是对的；但还不能据此直接确定消耗品如何运行。

例如玩家有12张炎爆符，需要能够回答：

> 放进阵盘的是全部12张，还是预先分配的4张？  
> 一叠4张符箓是一条CD，还是4条CD？  
> 能否把它分成两份、占两个位置？  
> 两个战斗入口能否同时引用同一份库存？

这些答案会明显影响构筑与消耗品价值，**不能由“可堆叠”三个字自动决定**。

## 04应该记录的最小关系

| 字段含义 | 必须区分的内容 |
|---|---|
| 库存总数量 | 玩家实际拥有多少 |
| 本场可用数量 | 哪部分允许在当前战斗中使用 |
| 本次消耗数量 | 一次成功提交使用成本扣多少 |
| 运行实例 | 谁拥有这条CD和控制状态 |
| 每战使用限制 | 与库存数量分开 |
| 耗尽处理 | 留空壳、移出、保留位置等，按明确规则选择 |

我建议的候选基线是：

> **一份上阵堆叠对应一个运行实例；堆叠数量不自动增加并行CD或攻击次数。**

但这属于**本轮建议**，此前没有明确确认，不应让Codex直接写成已定。

无论最后选哪种方式，都应保证：

> **同一件库存不能被重复复制到多个战斗入口；分装不增加数量；结算时未用完的数量不能重复返还。**

另外，上一版“数量归零后槽位默认保留”也应降为待确认策略。尤其要说明：耗尽的符箓是否仍算“相邻符箓”，能否继续触发位置条件。**有空壳不等于仍有可用器具。**

# 三、“成功使用后扣数量”必须明确为发动提交，不是效果命中

上一版写：

> 只有实际成功使用以后才扣除。

这句话容易被理解成：

> 火符没命中，所以不扣符；  
> 净化没找到目标，所以一定免费；  
> 攻击被完全吸收，所以不算使用。

应改成：

> **数量成本在该能力约定的支付节点提交；发动前资格检查失败，与发动后效果未命中、被抵抗、被吸收，是不同情况。**

01已经要求成本按整组检查和提交，实际发动事件不能先发布成功、再出现付费失败；退款也必须关联具体支付记录，不能默认发生。:chatgpt-content-reference{index="0"} :chatgpt-content-reference{index="1"}

例如，一张攻击符已经合法发动并扣除数量，之后被闪避：

> 不能仅因未命中就自动返还。

对于“没有负面状态时是否允许吃净化丹”“满血时是否允许服回血丹”，应由**使用条件**明确控制，而不是等结果出来以后再倒推这次算没使用。

这里不需要04另造支付系统，只要引用01的成本组和失败策略即可。

# 四、三轴攻击模型保留，但“来源”不能重新压成一个混合枚举

新版强调：

> 来源＋攻击类型＋元素。

这个表达适合玩家和设计者理解，应该保留。

但示例中的`Attack_Source`混放了：

> 武器、法器、符箓、反击、追击、派生伤害。

其中“武器、法器、符箓”是来源类别；“反击、追击”是行为身份。**不能在生产结构里重新当成一个互斥字段。**

01已经明确把行为身份、伤害结算身份与因果来源分开。04不应为了简化示例又把它们合回去。:chatgpt-content-reference{index="2"}

## 盾反击应这样理解

| 维度 | 值 |
|---|---|
| 物品类别 | 防具 |
| 防具形态 | 盾 |
| 行为身份 | 反击 |
| 攻击类型 | 钝击 |
| 攻击元素 | 按该反击效果定义 |
| 归属与因果 | 引用01的来源记录 |

文案可以简称“防具反击来源”，但数据应能回答：

> 它既是防具产生的，也是一次反击。

同样，**盾反击固定钝击，不等于所有防具产生的反击都被强制改成钝击**。你确认的是盾的规则，不是全部防具反制能力的统一类型。

# 五、“一次攻击”“一个伤害包”“一个元素分量”仍然不能混用

这是新版04里第二个比较重要的结构问题。

上一版说动画三下不自动算三次攻击，这条正确；但随后又把“三个独立攻击包”与“三次攻击行为”放得太近。

应明确：

> **多份伤害包，不必然等于多次发动，也不必然等于多次命中判定。**

01已经区分：

> 因果链 → 行动 → 结算轮 → 伤害包。

例如连携后续节点B本体与追加包虽然是不同伤害包，却共享同轮防御边界。:chatgpt-content-reference{index="3"}

因此04需要保留以下边界：

| 内容 | 不应自动推导成 |
|---|---|
| 消耗3枚暗器 | 发动3次 |
| 动画连续命中3下 | 产生3次攻击事件 |
| 一次攻击附带一个额外伤害包 | 再支付一次基础武器费用 |
| 一个攻击带两种元素 | 两次独立攻击 |
| 为数据方便拆成两行伤害 | 自动触发两次“攻击发动”监听 |

**攻击次数、命中次数、伤害包数量和数量成本，必须各自引用明确的动作结构。**

# 六、多属性武器不能被04的单值`Element`示例顺手删掉

你这轮严格限制的是：

> **每件防具在同一时点只能有一种防具元素，或者无属性。**

不是所有攻击都只能有一个元素。

上一版虽然口头保留了武器多属性，但字段表大量使用单值`Intrinsic_Element`、`Attack_Element`，后续可能被整理成只允许选一个元素的下拉框。

因此应明确区分：

| 对象 | 元素约束 |
|---|---|
| 单件防具当前防御元素 | 单值：无属性或七系之一 |
| 角色当前身甲元素 | 按防具贡献与并列扫描得出的单值 |
| 攻击元素 | 按具体攻击规格，可保留已经允许的多元素设计 |
| 物品检索用属性标签 | 不直接等于真实伤害分配 |

多元素攻击还必须说明各元素对应的伤害量或分配方式。不能把一个100伤害的攻击标上火、雷以后，就变成：

> 100火伤＋100雷伤。

**攻击类型四选一，和攻击元素怎样组成，是两件事。**这次简化前者，不能顺便改掉后者。

# 七、`Has_Attack=False`不等于“绝对不会造成伤害”

上一版把“没有攻击”与“攻击类型为空”连在一起，处理普通回血丹没有问题，但对状态、反伤和持续效果不够准确。

例如一个器具可以：

> 不发动直接攻击，只施加一个之后会结算伤害的状态。

因此至少要区分：

> **是否创建攻击行为。**  
> **是否包含伤害效果。**  
> **该伤害是否参与甲型判定。**

这不是新建另一套伤害类型，而是防止把所有伤害都包装成一次主动攻击。

01本来就区分了“直接伤害”和“创建完整攻击”；独立附伤也不自动继承原武器的普通暴击资格。:chatgpt-content-reference{index="4"}

尤其迁移时要注意：

**状态跳伤不能仅因不是斩击、穿刺、钝击，就自动新增一遍法术型甲型修正。**它原来走什么结算通路，需要按该状态规则核对。

同样：

> 支付气血成本、换装导致护甲截除、修改资源上限，

不应为了“填满Attack Type”而被伪装成一次伤害攻击。

# 八、“Attack Type只管甲型”应改为“主要决定甲型交互”

上一版用了“唯一基础职责”这个说法，略显过头。

我们以后完全可能设计：

> 每发动3次钝击型攻击，触发效果。  
> 相邻斩击武器获得某种强化。  
> 受到法术型伤害后积累进度。

这些都需要按攻击类型过滤。

所以正确口径应是：

> **Attack Type主要用于甲型交互，也可以被明确的机制条件读取；但它不自动决定来源、命中、暴击、功法身份或共鸣资格。**

这样既保留你要的四类清晰结构，也不会误删已有的类型联动设计空间。

同理，元数据标签只能帮助检索。**把物品打上“恢复”或“法术型”标签，不等于自动获得对应能力或结算资格。**

# 九、物品实例还需要区分“永久个体数据”和“本场运行数据”

上一版为了讲消耗品，分成：

> 物品模板、库存堆叠、战斗实例。

但对于仙品，这还少了一层明确说明。

例如择相仙甲：

> 已修复到第几阶段、已经解锁哪些属性，

属于这件仙甲的**持久个体数据**。

而：

> 本场选择水属性、当前被冻结多久、当前CD，

属于**本场运行数据**。

建议概念上这样区分：

| 数据层 | 典型内容 |
|---|---|
| 物品定义 | 名称、器型、固定尺寸、基础规格、成长方案引用 |
| 持久个体 | 这件仙品的成长阶段、已解锁形态、专属培养结果 |
| 库存数量 | 可堆叠消耗品的实际件数 |
| 战斗运行 | 本场CD、控制、计数、当前生效形态／元素 |

**不是要求每件普通丹药都建立复杂个体档案，也不是要求复制四份数据。**只是不能把仙品成长进度误放进战后清空的运行层。

此外，只有规格与持久数据兼容的东西才能堆叠。同名不自动意味着可合并；不同成长阶段的器具不能因为名称一样就丢掉个体差异。

# 十、防具聚合规则已经确定，但择相仙甲有一个必须说明的交接点

你已经确认：

> 各元素按防具占格统计；最高并列时按阵盘扫描决定。

那么普通情况下，择相仙甲改变的是：

> **这件仙甲当前贡献什么元素。**

之后角色主属性仍然要重新走聚合。

例如：

> 仙甲4格，本场选择水；其他火属性防具合计5格。

按当前普通聚合规则：

> 角色最终仍然是火属性身甲。

所以不能同时写：

> “仙甲选择水”  
> “角色必定成为水属性”

而没有额外规则。

## 这里有两种不同的仙品设计

**遵守聚合的择相甲：**

> 自由选择自身元素贡献，通过搭配其他防具决定角色主属性。

**具有主属性指定权的择相甲：**

> 它明确获得一项特殊权限，可以指定角色最终身甲属性。

第二种比第一种多了一项规则权力。**现在不能默认附赠。**

04应先准确记录普通聚合；仙品正式设计时，再决定它究竟获得哪一种能力。这样既保留你喜欢的仙甲方向，也不会让普通规则与仙品描述暗中冲突。

# 十一、护甲换装截上限，还要补两个执行边界

你已经确认的规则不变：

> 按新装备计算上限；当前护甲超过新上限就截到新上限；上限提高不自动补甲。

需要补的是怎样执行，避免程序实现制造额外结果。

## 1. 一次合法替换，只按这次操作的最终装备结果结算

如果系统支持“一次替换”，就不能内部先把旧防具全部移除、把护甲截到0，再加入新防具。

例如：

> 当前80／100，一次替换后新上限90。

应得到：

> 80／90。

不能因为程序内部经过一个临时空装备集合，得到0／90。

但如果玩家真的进行了**两次独立操作：先移出，再装入**，就分别按两次实际操作结算，不能假装中间的卸下从未发生。

## 2. 容量截除不等于受到攻击

换装导致护甲从80截到60，应记录为：

> 装备／上限变化导致的护甲减少。

不能自动触发：

> 被敌人攻击、实际承伤、护甲受击反击。

否则玩家反复换装就可能免费积累受击收益。

这里可以复用01的实际变化与原因记录，不需要再创造一套事件。

另外，**护甲降到0不自动改变仍在上阵防具的甲型与元素贡献**。护甲当前值与装备集合继续分开。

# 十二、主甲型与主元素的两套决胜方式，必须始终分开

这一点新版第1批写对了，但值得作为自动校验项保留：

| 对象 | 最高并列时 |
|---|---|
| 主甲型 | 玩家从并列甲型中指定 |
| 主身甲元素 | 只在并列最高元素中，按阵盘扫描决定 |

不能为了统一程序函数，就把其中一套悄悄改成另一套。

还需要一个实现衔接：**敌方不会进行玩家式手动选择。**敌方甲型并列时，应有合法的预设选择或明确的决胜规则，不能让程序随机挑一个。

这是敌方配置需要补的字段，不需要重新讨论你的玩家侧规则。

同时，玩家之前指定的甲型如果已不在当前并列候选集合里，也不能继续生效。

# 十三、法器与丹药的分类还有两处小的维度混用

## 法器的三种运行模式只能做“常用组合”，不能互斥

上一版把法器分成：

> 主动轮转、被动监听、常驻／维持。

作为阅读提示可以，但不能做成只能选一个的枚举。

因为：

> 常驻属性修正，不等于监听；  
> 静态领域，不等于持续支付的维持能力；  
> 一件法器可以同时有轮转动作和事件监听。

法器仍应逐个能力引用01的发动结构。04只标它主要具备哪些运行方式，不再造一套精简但不兼容的M01。

## “永久／成长药效”不能全部当成持续Buff

例如重置功法的丹药，是：

> 使用一次，执行一次成长数据修改。

不是在角色身上挂一个永久“重置Buff”。

因此丹药需要分别记录：

> **效果执行方式**与**结果保存范围**。

即时执行也可能产生长期结果；持续药效也不一定跨战。两者不要绑成一个字段。

# 十四、独立迁移清单需要加一道重要保护：迁移法术本体，不迁移它调用的一切

上一版迁移清单写：

> 真正的功法法术统一采用法术型攻击。

对功法法术的主体伤害，这是本轮方向。但Codex不能把它机械扩展成：

> 凡是由某门法术引起的后续攻击，全部改成SPELL。

例如御兵术调用武器额外攻击，01明确：这是实际的武器来源攻击，仍检查武器自己的条件、费用，并保留因果谱系。:chatgpt-content-reference{index="5"}

所以应区分：

| 原行为 | 迁移处理 |
|---|---|
| 原先带物理甲型标签的功法法术本体伤害 | 按新规则迁移到法术型 |
| 法术调用一把剑执行武器攻击 | 仍是被调用剑的斩击 |
| 法术触发盾的钝击反击 | 不因父事件是法术就改成法术型 |
| 法术产生状态，状态之后跳伤 | 检查状态既有通路，不机械套主体迁移 |
| 原条件要求“穿刺法术” | 列出受影响能力，不能自动扩成“所有法术” |

**因果来源不是攻击类型。**这条迁移时尤其要坚持。

## 旧双标签也不能靠“补一个物理包”偷偷保留

迁移以后，不能为了维持旧收益，自动把原穿刺法术改成：

> 一份法术型伤害＋一份额外穿刺伤害。

否则虽然每包四选一，实际上又把旧结构绕回来了，还增加了事件数量和伤害。

只有已经明确设计为两个独立效果的能力，才保留两个效果。**迁移阶段不新增补偿伤害包，不自行重平衡。**

---

# 十五、法术型效率迁移不能顺手改变公式的组合方式

你确认的是：

| 法术型面对 | 效率 |
|---|---:|
| 无甲 | 110% |
| 轻甲 | 100% |
| 重甲 | 100% |
| 灵甲 | 90% |

这次更新的是对应的甲型修正值，**不是自动新建一个与所有其他修正连乘的乘区**。

已有01强调：修正类型与完整计算顺序分开，独立乘区必须明确，不能因为字段看起来像倍率就自行换公式。:chatgpt-content-reference{index="6"}

迁移时还应检查：

> 原法术的物理甲型修正已经移除；新的法术型修正只应用一次；元素克制继续按原规则；命中、暴击、共鸣资格不因此扩大。

也不要把我前面提出但你没有采纳的“法术对灵甲85%／物理对灵甲115%”混进来。**新的明确结果只有你确认的这一行；三种物理攻击原有矩阵不由这次提案重写。**

---

# 十六、新的攻击类型必须同步到控制与监听，但不能把沉默扩大成“封锁所有SPELL攻击”

这是迁移清单需要额外点名的一项。

当前02区分：

> 禁用针对道具；沉默针对法术。

01也明确撤回了旧“沉默只封武器附加效果”的候选解释。:chatgpt-content-reference{index="7"}

因此：

> 一张炎爆符打出法术型攻击，仍然是符箓物品，不因`Attack_Type=SPELL`自动变成沉默的法术对象。  
> 一件雷珠法器打出法术型攻击，仍按法器的来源与控制范围检查。

同理，监听条件要明确到底查：

> 攻击类型为法术型；  
> 来源是功法法术；  
> 还是使用了符箓。

迁移这三个概念时，不能互相替换。

还要同步检查03里的旧例子：蓄势已经撤销，耐久、旋转、射程现在也有了你的明确决定，不能继续以“高品级预留能力”的身份从旧矩阵里重新出现。

不过，**“不需要武器射程”不等于删除阵盘上的邻接、同行或距离范围**。批量搜索`Range`时必须区分这两种用途。

---

# 十七、字段层需要收束，不要同一数值保存三份

新版04一处让武器表保存基础攻击、CD、元素；另一处又让`Attack_Profile`包含这些内容；最后又有独立攻击规格。

如果照着三个位置都填，迟早会出现：

> 武器主表伤害20，攻击模板伤害25。

建议统一为：

> **全局规则模板**保存通用判定规则。  
> **具体物品的动作／效果记录**保存这件物品的具体伤害、费用等参数。  
> **运行实例**保存当前值和临时修正。

每个实际参数只能有一个权威来源，其他表通过引用或显示视图读取。

另外，字段状态还应补清楚：

| 情况 | 表达 |
|---|---|
| 不适用 | 例如纯辅助行为没有攻击类型 |
| 已确定为零 | 例如0体力费用 |
| 尚未决定 | 明确待定，不用空白冒充零 |
| 由规则推导 | 例如剑的基础攻击类型 |
| 运行时产生 | 例如当前CD |

`NONE`只表示没有攻击类型的适用对象，不是合法伤害可以随意选择的“第五种类型”。

04中示范的英文ID也应继续标为**设计标识**。Codex接入现有项目时需要做映射，而不是认定这些示范名称已经是生产接口。

---

# 十八、这次应该增加的反向检查案例

这些是**应满足的文本与配置检查条件**，不是已经运行通过的游戏测试。

| 案例 | 应检查的结果 |
|---|---|
| 一叠符箓放入阵盘 | 数量消耗与占格独立，不因是消耗品就免除上阵要求 |
| 攻击符合法发动后未命中 | 按已提交成本处理，不自动返还 |
| 消耗3枚飞针 | 消耗数量不自动等于3次发动事件 |
| 一次攻击附带额外伤害包 | 不自动多付一次费用或多计一次攻击发动 |
| 多元素弓 | 攻击类型保持唯一，元素分量不重复计算完整基础伤害 |
| 仙品成长后结束战斗 | 清战斗状态，不清成长阶段 |
| 水择相甲4格＋火防具5格 | 普通聚合结果仍是火，除非仙甲明确拥有主属性指定权 |
| 一次换装80／100→新上限90 | 结果80／90，不因内部中间态被截到0 |
| 换装导致护甲截除 | 不自动触发“受到敌方攻击”收益 |
| 御兵术调用剑 | 被调用攻击仍是斩击，不因法术父事件改为SPELL |
| 法术型符箓遇沉默 | 按来源与控制Scope检查，不按SPELL一概封锁 |
| 原“穿刺法术增益”迁移 | 单独列出复核，不自动扩大为全部法术增益 |

---

## 最终判断

**04的核心结构可以保留，不需要第三次重写。**这轮需要处理的重点是：

> **消耗品是否上阵与是否消耗分开；来源类别与行为身份分开；攻击次数与伤害包分开；持久物品数据与战斗数据分开；普通防具聚合与仙品特殊权限分开。**

其中大部分是直接澄清原意，不是增加玩法。

真正还需要在具体资产落地前确认的，主要是**消耗品的上阵数量／CD组织、耗尽后的占位策略，以及择相仙甲是否获得超越普通元素聚合的指定权**。这些应单列，不让Codex自行选答案，也不必阻止我们继续设计其他物品。

可以把这轮给Codex的整理原则压成一句：

> **保留新版04已确认的分类和数值，合并本次接口修正；不新增攻击包、不改变事件次数、不自动扩大控制或监听资格、不把消耗品另造为免占格系统；未决玩法明确保留，通用算法继续引用01／02。**

这样修订后，04才能真正成为后续材料、打造和物品主表的稳定依据，而不是另一份需要设计者临时猜测的长说明。
