建议把T01机制词典升级成这10个模块

这就是我现在认为比较稳的最终骨架：

模块	管什么
M01 发动范式	主动、周期、条件、待发、延迟、蓄势、被动、消耗
M02 事件系统	监听什么事件、事件处于哪个结算节点
M03 资格过滤	属性、来源、命中、伤害门槛、类别等
M04 积累系统	计数、累计量、阶段值、充能、事件记忆
M05 目标与空间	指定、随机、邻接、方向、行列、领域、尺寸
M06 效果行为	伤害、恢复、状态、净化、反击、CD、冻结、规则修改
M07 时序与生命周期	延迟、蓄势、中断、刷新、重置、战后清空
M08 资源与成本	灵力、体力、次数、充能、支付时点、退款
M09 叠加与链控制	同名叠加、互斥、递归、每事件触发上限
M10 来源与可见性	效果来源、所有者、派生资格、玩家是否可见

我觉得到这里才真正适合作为第一步的“机制词典骨架”封版。

它的好处是，我们以后拿任何一个怪物掉落材料、任何一件武器、法器、防具甚至丹药过来，都能按照这十块把它拆清楚。

而且它不是为了让每件物品都复杂成十层。恰恰相反：

下品可能只用M06；凡品用2～3块；良品开始明显使用M02/M03；上品开始使用M04/M05/M07；灵品开始跨模块联动；玄品则可以直接修改M01/M02/M09这些底层规则。

这个和我们现在的品级进阶逻辑会非常契合。

所以如果你认可，我认为T01机制词典的“骨架层”可以到这里先封住，下一步再不是继续加词，而是开始为这10个模块分别建立标准枚举词条。比如先把M01“发动范式”逐个定准确，然后M02事件系统，最终就能直接进入Excel。

好，T01  下的这些m01-m10，能一次对话出完，还是分批次对话出？

可以一次性全写出来，但我不建议一口气把 M01～M10 全部定完。这十块已经接近整个物品系统的“底层语法”，如果一次塞完，很容易出现前面定义了一个词，后面又发现要改，最后内部互相打架。

我更建议：**同一个对话线程里，分 5 批完成。**这样上下文不断，又能逐批审查。

批次	内容	原因
第1批	M01 发动范式 + M02 事件系统 + M03 资格过滤	三者共同回答“什么时候触发、什么事件算、什么事件不算”，应该一起定
第2批	M04 积累系统 + M05 目标与空间	计数/充能/累计量，以及邻接/行列/阵位/目标选择，彼此关联
第3批	M06 效果行为单独做	这是最大的一块，会包含伤害、恢复、状态、净化、反击、CD、冻结、来源修改、连携修改等，值得单独认真做
第4批	M07 时序与生命周期 + M08 资源与成本 + M09 叠加与链控制	共同解决“怎么运行、怎么中断、怎么付费、会不会递归爆炸”
第5批	M10 来源与可见性 + 全词典交叉审查	最后检查来源归属、玩家可见信息，以及M01～M10有没有冲突和遗漏

我尤其不建议把 M06 跟其他九块一起快速带过。它以后基本就是我们所有物品的“效果积木库”，可能最后会有几十种标准效果行为。

每一批我会采用同样的结构：

正式定义 → 标准枚举 → 默认规则 → 可配置字段 → 典型例子 → 高品级可扩展方向 → 和现有七系规则的冲突检查

而且我们不用每一个小词都让你回答一道选择题。**我先把一整批整理成成熟方案，你只挑真正涉及设计取舍的地方确认。**这样不会变成几十轮机械问答。

M01｜发动范式 Activation Pattern

M01回答的是：

“这个物品/效果是通过什么方式获得一次执行机会的？”

它不回答造成多少伤害，也不回答监听什么细节。

我建议正式保留 9种基础发动范式。复杂物品可以组合，例如“周期CD→待发→蓄势”，而不是为每个组合重新造一个名词。

编码	正式名称	定义	典型用途
M01-01	周期轮转	自身CD完成后获得正常发动机会	武器、主动法器、部分符箓
M01-02	条件触发	没有固定周期，指定事件出现时直接尝试发动	受击反击、破盾触发
M01-03	周期待发	先完成自身CD，再等待指定事件；事件出现才实际发动	反击法器、预备型器物
M01-04	被动常驻	不产生独立发动事件，持续修改规则或属性	命中＋%、状态容量＋N
M01-05	开关维持	主动开启某种持续状态，关闭/资源不足/其他条件时结束	领域法器、高阶维持型器具
M01-06	开战执行	战斗开始时满足条件即执行一次	初始护盾、初始充能、布阵效果
M01-07	消耗使用	使用实体数量、耐久或次数取得一次发动	丹药、符箓、暗器
M01-08	延迟生效	已经成功发动，只是实际效果在N秒后落地	延时爆炸、埋雷
M01-09	蓄势发动	开始执行后进入准备过程，完成后才真正产生核心效果	重炮、蓄力法器、阵盘大招
M01-01 周期轮转

就是目前战斗系统最普通的方式：

完整CD → 获得发动资格 → 实际发动 → 重开完整CD。

手动模式与自动模式不是两种发动范式，而是同一范式的操作模式。

所以将来Excel应该拆开：

发动范式：周期轮转
操作模式：自动/手动可切换

现行规则已经确认普通物品可分别切换手动/自动；预备式则使用开启/关闭，实际发动才支付资源。

M01-02 条件触发

定义：

指定事件发生时立即检查资格，没有“先走完本器具普通CD”这一前置过程。

例如：

自身第一次受到暴击时获得护盾。

或者：

敌方护甲归零时，对其追加一次攻击。

但这种器具仍然可以有：

触发内置CD。

例如：

被攻击时反击，内部CD 5秒。

所以要区分：

轮转CD与触发冷却。

后者只是限制条件效果多久能再次发生，并不意味着器具在像武器一样自动轮转。

M01-03 周期待发

这个非常重要，会大量用于我们的法器和防具。

结构：

走完CD → 进入待发 → 等事件 → 实际发动 → 重开CD。

例如：

CD 8秒。完成后等待自身被攻击。下一次被攻击时产生护盾。

这直接继承现有预备式逻辑：

待发期间不开始下一轮CD；
没有实际发动不支付发动成本；
资源不足时可以继续等待；
控制效果可能阻止实际发动。

所以我们以后不再为法器重新发明一套“准备状态”。

M01-04 被动常驻

不产生一次“器具发动”。

例如：

相邻穿刺武器命中＋10个百分点。

自身毒蚀容量＋5。

雷盾吸收率＋10个百分点。

这里特别重要：

被动修改≠监听。

如果效果是：

相邻武器发动后，我获得1充能。

这是监听。

如果是：

相邻武器攻击＋10%。

这是被动规则修改。

M01-05 开关维持

我建议现在补进来，因为以后领域型法器很可能需要。

例如：

开启【聚灵领域】：领域内法器CD－10%；每秒消耗2灵力。

它不是普通周期器具，也不是单次法术。

结构是：

开启 → 维持状态 → 持续支付/检查条件 → 关闭。

可能存在：

手动关闭
资源耗尽关闭
被控制关闭
离开阵盘关闭

这些具体退出规则放M07/M08。

灵品、玄品尤其适合这种范式。

M01-06 开战执行

专门处理：

开战时获得X。

与普通轮转严格区分。

例如：

开战获得10点灵障。

开战记录同行武器数量。

开战给相邻两件器具各1充能。

默认：

每场战斗一次。

战斗中重新放入器具不能自动当作“第二次开战”。

如果以后需要“入阵触发”，那属于M02的【入阵事件】，不是开战效果。

M01-07 消耗使用

丹药、符箓、暗器都会大量用。

核心定义：

发动本身消耗一个实体数量/使用次数。

它仍然可以附带CD。

例如：

符箓有3张，每次发动消耗1张，CD 6秒。

所以：

消耗品 ≠ 无CD。

至于什么时候扣数量、被打断返不返，放M08。

M01-08 延迟生效

一定要和蓄势分开。

例如：

放下一枚火种，3秒后爆炸。

只要最初动作已经成功：

默认不会因为施术者后来中了虚弱而取消。

之后发生的是一个已经排入时间轴的延迟事件。

M01-09 蓄势发动

例如你提出的：

发动后准备3秒，3秒完成时造成重击；过程中受扰乱则失败。

重点：

核心效果尚未成立。

所以它可以被中断。

蓄势以后还能和其他机制组合：

蓄势期间获得护盾；
相邻法器使蓄势－0.5秒；
连续被攻击两次则蓄势失败；
蓄势完成时根据期间累计值决定伤害。

这些都是非常适合灵品/玄品的东西。

M01补充：操作模式不是发动范式

另外单独保留字段：

操作模式

建议枚举：

自动
手动
自动/手动可切换
开启/关闭
强制自动
无操作

例如：

普通武器：

周期轮转＋自动/手动可切换。

反击法器：

周期待发＋开启/关闭。

纯被动：

被动常驻＋无操作。

这样会非常干净。

M01第一次自检

我们现在已经能描述：

普通武器轮转；
手动武器；
反击器具；

M02｜事件系统 Event System

M02解决：

“战斗和修炼中，到底发生了哪些可以被监听的标准事件？”

我认为这是第一批里最重要的部分。

这里不能只做一个“事件名称表”，还应该正式引入：

原始事件、子事件、事件节点

例如一次武器攻击：

原始事件：

武器A的一次主动攻击。

里面可能产生：

发动成功
命中
暴击
特殊盾受损
破盾
扣甲
伤血
施加状态
触发反击
产生追击

这些都是这个原始攻击里面的子事件。

这样以后：

“每发动一次攻击”

默认只读原始攻击一次。

“每破一层盾”

则读破盾子事件。

这就彻底解决之前担心的“一击被计数五次”。

EVT-T03	训练器具实际发动
EVT-T04	训练攻击命中模拟目标
EVT-T05	训练支付灵力
EVT-T06	训练支付体力
EVT-T07	完成一次合格训练动作
EVT-T08	训练停止

这里我建议特别坚持：

修为不要监听“任何地方消耗体力”。

而应该监听：

【合格修炼场景】＋【训练行为】＋【实际发动/支付】

这样就不会出现：

在战斗里疯狂耗体力也自动刷“静修经验”

这种奇怪情况。

正式修为公式以后再放T03。

M02的“事件计量值 Payload”

事件除了“发生了”以外，还要携带数值。

例如：

【护甲实际承伤】

可以携带：

本次损失12.5护甲。

【获得状态】

可以携带：

获得4层灼烧。

【资源恢复】

携带：

实际恢复8.2灵力，溢出3.0。

这非常重要，因为M04以后可以做：

每累计损失50护甲……

而不是只能：

每被打5次……

所以标准事件至少允许携带：

次数、实际数值、层数、持续时间、来源ID、目标ID、属性/标签。

M02第二次自检

拿我们已经讨论过的东西逐个测试：

3次火攻→火球：
EVT-A01攻击实际发动，可表达。

被攻击3次→冻结1×1：
可选监听“敌方攻击实际发动”“自身被命中”或“自身出现实际伤害”，可以精确区分。

毒蚀完成3次跳伤：
EVT-S06，可表达。

破盾反击：
EVT-D02，可表达。

丹药耗尽触发：
EVT-I16，可表达——这也是参考Excel里值得保留的一类触发思想。

稻草人训练：
EVT-T03～T07，可表达。

连携成立后充能：
EVT-C04，可表达。

第一次掉到30%血：
EVT-R13，可表达。

目前没有发现重要触发场景缺失。

M03｜资格过滤 Eligibility Filter

M03回答：

“事件已经发生了，但它是不是这件物品需要的那一种事件？”

这是监听系统真正防止失控的地方。

例如：

每3次火属性攻击……

如果没有M03，我们马上就会遇到：

雷击算不算？
火焰反击算不算？
独立附炎算不算？
法器火球算不算？

所以我建议M03固定为 9组过滤器。

M03-01｜环境/场景过滤

首先判断这个效果在哪儿有效。

标准值建议：

战斗
非战斗修炼
制作/生产
世界探索
城镇
任意场景

默认战斗器具：

仅战斗。

修炼效果必须明确：

非战斗修炼。

这样也解决刚刚的“耗体力得修为”边界。

M03-02｜阵营过滤

事件来源：

自身
己方
敌方
任意

事件目标也可以另外判断：

指向自身
指向己方
指向敌方。

例如：

“敌方火属性攻击命中自己3次。”

就不是简单的“监听火攻”。

M03-03｜来源大类过滤

事件来源可以按：

角色
武器
防具
法器
法术
丹药
符箓
暗器
功法效果
状态
连携追加包
环境/剧情

这里要注意：

防具通常没有普通主动攻击，但可以成为：

反击来源。

所以“物品类别”和“攻击来源类型”还要继续分。

M03-04｜攻击来源身份

这是非常关键的一层。

建议至少提供：

主动武器本体
主动法术本体
主动法器攻击
暗器攻击
符箓攻击
防守反击
二次追击
独立属性附伤
状态持续伤害
状态派生攻击
连携追加包
其他派生伤害

以后装备描述可以很精确：

“己方主动武器本体造成火属性伤害时……”

与：

“任何己方火属性伤害……”

是两种完全不同的强度。

M03-05｜属性与伤害标签过滤

属性：

无属性
金木水火土风雷
任意属性
指定多个属性

物理标签：

穿刺
斩击
钝击

还应该支持组合判断：

火属性且斩击
风属性或雷属性
穿刺武器但不限属性

以后双属性武器也自然可以：

属性标签 = 风 + 雷

不需要创造“风雷”这个新基础属性。

M03-06｜事件结果门槛

这是最容易写含糊的地方，我建议以后强制从标准门槛选择：

门槛	含义
发动成功	只要器具实际发动
命中	必须命中，不要求正伤害
造成任意正数实际损失	盾/灵障/甲/血任一项实际减少
实际破盾	至少击破一层/一种盾
实际扣甲	护甲落账损失>0
实际伤血	气血落账损失>0
击杀	目标死亡
状态施加成功	实际增加至少1有效层/状态成立
状态结算成功	状态自身完成有效一次结算

于是以后绝对不再写模糊的：

“攻击到敌人时……”

而是写：

命中时。

或者：

实际伤及气血时。

M03-07｜器具属性过滤

这是指事件来源那件器具的固有资料。

可以过滤：

品级
类别
子类
尺寸
占格数
是否带CD
是否消耗品
是否有某机制标签
是否处于待发/蓄势/冻结等状态

例如：

相邻的1×1穿刺武器发动时……

就由M03过滤来源资格。

注意：

“相邻”本身还是M05空间机制。

M03只负责：

对方是不是1×1穿刺武器。

M03-08｜状态与资源前置条件

事件发生时还可以要求：

自身有/没有某Buff
目标有/没有某Debuff
状态层数≥N
状态层数=N
气血低于X%
灵力高于X
有护盾/无护盾
护甲>0/护甲归零

这里必须明确：

默认读取事件发生前还是发生后。

我建议统一提供字段：

读取时点 = 事件前 / 事件后

例如：

攻击“已有灼烧”的目标。

就是：

攻击前快照。

而：

命中后目标灼烧达到10层则……

就是：

事件后读取。

这个很关键。

M03-09｜派生与递归资格

M09以后会专门管触发链，但M03必须先能过滤：

原始事件
派生事件
两者均可

比如：

“每3次主动火攻发射火球。”

默认可以限定：

仅原始主动攻击。

火球本身即使也是火伤，也不会重新给这个计数＋1。

而另一个高阶法器可能明确写：

“任何火属性伤害，包括派生伤害。”

那才允许。

这样一来，绝大多数无限循环在M03阶段就已经被堵住。

一个完整标准例子

现在把：

阵盘发动3次火属性攻击后，法器释放火球。

翻译成M01～M03：

M01

发动范式：
条件触发。

M02

监听事件：
EVT-A01 攻击实际发动。

M03

场景：
战斗。

来源阵营：
己方。

来源身份：
主动攻击。

属性：
火。

来源资格：
武器/法术/法器皆可——如果该物品以后如此设计。

结果门槛：
不要求命中。

派生资格：
仅原始主动攻击；派生火球不计。

然后M04才写：

计数3次。

M06写：

发射火球。

这就是我们想要的“积木系统”。

再测试一个复杂例子

自身被敌方实际伤及气血3次后，随机冻结敌方1件1×1器具2秒。

M01

条件触发。

M02

监听：
EVT-D07 气血实际受损。

M03

来源阵营：
敌方。

事件目标：
自身。

实际伤血：

0。

重复攻击的多个伤害包是否分别计：
以后由M04/M09定义。

M05：
随机敌方1×1器具。

M06：
器具冻结。

M07：
2秒。

非常清楚。

第一批最终交叉审查

我最后再用几个容易出问题的案例反向检查。

检查下来，我没有发现M01～M03还存在明显结构缺口。

尤其是我认为这批里最值得固定的三个设计原则：

CD完成 ≠ 实际发动。
命中 ≠ 实际造成伤害。
发生一个事件 ≠ 自动拥有监听它的资格。

只要这三层一直分开，后面法器再复杂，体系也不容易乱。

因此我建议把这版作为 M01～M03第一版基线。下一批进入 M04积累系统＋M05目标与空间系统，会正好接上你前面最关心的“3次触发、充能、邻接、上下左右、阵盘边缘、随机冻结1×1器具”这些机制。
