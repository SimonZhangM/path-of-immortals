**有，而且有几处需要真正修正，不只是再补几个词条。**把五批内容连起来看，M01～M10 的大框架可以保留，但我上一轮说“已经闭合，可以作为正式版”的判断偏早了。

目前最准确的定位应当是：

> **机制覆盖比较完整的草案，经过本轮修正后，再合并成统一版本。**

主要问题不是缺少第十一个模块，而是：**有些分类混用了不同维度；部分通用规则可能覆盖既有定案；个别例子确实写错；还有一些“预留能力”被我写得像已经决定要做。**

下面按模块给出这次的整体审查结果。涉及既有规则的地方直接纠正；涉及新的玩法取舍，仍然标为建议或待定，不借复查替你作决定。

# 一、M01：发动范式要保留，但不能作为九选一的分类

之前并列了“周期轮转、条件触发、周期待发、被动常驻、开关维持、开战执行、消耗使用、延迟生效、蓄势发动”。

这些词都需要，但**不属于同一个分类维度**。

例如一张符箓可以同时满足：

> 每8秒获得发动机会 → 自动开始蓄势2秒 → 消耗一张 → 完成后攻击。

它同时属于“周期轮转、蓄势、消耗品”。如果 Excel 只有一个“发动范式”下拉框，就无法准确填写。

## 修正方式：M01内部改成组合结构

| 维度         | 回答的问题             | 例子                |
| ---------- | ----------------- | ----------------- |
| **发动机会来源** | 什么使它尝试发动？         | 轮转到点、指定事件、手动开启    |
| **就绪门槛**   | 是否要先完成入阵、CD或进入待发？ | 先完成8秒CD，再等破盾      |
| **执行过程**   | 取得机会后怎样执行？        | 即时、延迟、蓄势、持续维持     |
| **操作模式**   | 玩家怎样控制？           | 手动／自动切换、开启／关闭、无操作 |

“开战执行”归为监听战斗开始事件的常用模板；“消耗使用”的数量扣除放M08。“被动常驻”仍保留为不需要独立发动事件的模式。

**原来的九个术语不用删除，但不能把它们做成互斥选项。**

另外，我之前举过“下品可能只用M06、良品才开始用M02/M03”的说法，也应删除。普通木棍同样需要发动、CD、体力费用和来源记录。**品级限制的是玩法能力与联动复杂度，不是能使用哪些数据模块。**

# 二、M02＋M03：需要把“事件谱系”和“战斗来源身份”彻底分开

前文有一个容易造成严重误判的地方：

> 有上游事件、被别的效果触发出来的攻击，容易被统一当成“派生伤害”。

实际上，**“由谁触发”不等于“按什么战斗来源结算”。**

例如御兵术调用武器额外攻击，这次攻击虽然由法术触发，但既有规则明确它是真正的武器来源，可以触发符合条件的锋痕、失衡追击，并不改变被调用武器正常CD。不能因为它有一个法术父事件，就把它降为普通派生包。

## 应拆成四个独立问题

| 字段         | 说明                         |
| ---------- | -------------------------- |
| **器具类别**   | 这件东西是武器、法器、防具、符箓还是法术       |
| **本次行为身份** | 普通攻击、外部调用的额外攻击、追击、反击、持续跳伤等 |
| **伤害结算身份** | 武器本体、法术本体、独立附伤、连携追加包等      |
| **事件因果来源** | 这次行为由哪个事件、哪个效果促成           |

因此，“自动触发的法器火球”到底拥有怎样的命中、共鸣、状态触发资格，必须引用明确的**来源规则模板**，不能单凭“自动”或“有父事件”决定。

### 还需要增加“同轮结算”的标识

之前有 `Root_Event_ID`、`Parent_Event_ID`，但还不足以表达我们的防御体系。

至少应区分：

> **因果链 → 一次发动／攻击 → 本轮结算 → 独立伤害包。**

原因很具体：连携追加包虽然独立计算，但与后续节点B本体属于同一轮；B打空最后雷盾后，追加包不能立刻切换到灵障，待转雷蕴也要等这一轮结束后才生新盾。仅凭“它是一个新伤害包”或“它和B有同一个Root”，都不足以正确处理。

### M02还应补齐“执行结果”，而不只是成功／失败

例如施加灼烧，可能出现：

> 命中成功；新增层数为0；但持续时间成功刷新。

治疗也可能：

> 治疗尝试发生；实际恢复0；但触发了重伤相关处理。

所以事件至少区分**尝试量、实际增加／扣除量、溢出或浪费量、是否刷新、未执行原因**。不能用一个“成功”字段代替全部结果。现有规则已经明确，满血时的治疗尝试仍可能进行重伤与伤势反噬处理。

最后，器具发动事件与攻击发动事件可以同时存在，但必须关联同一次行动。某监听器用“器具发动或攻击发动”作为条件时，不能把同一次武器发动重复计两次。

# 三、M04＋M09：计数、触发机会、防递归之间还没有完全接好

这是这轮最需要修正的接口。

前文一方面规定：

> 一次累计跨过多个门槛，产生多个触发机会。

另一方面又规定：

> 同一个Effect实例在同一Root中默认最多成功触发一次。

两条直接组合，会导致**M04算出了两次机会，M09却吞掉一次**。

例如现有【风过无尘】，一次实际驱散12层，确实可以产生两次延后机会、留下2层计数，而且两次可以作用同一目标。不能让通用防递归规则把它改成一次。

## 修正：把三种限制拆开

**第一种是事件去重。**

同一个标准事件，因为重复通知、多个匹配标签等原因，被同一监听项看见多次，只记一次。

**第二种是计量单位。**

究竟按一次攻击、一份伤害包、一层破盾、一个目标，还是一次阈值机会计数，由机制明确指定。

**第三种才是反馈循环限制。**

用于防止：

> A产生效果 → B响应 → 再次回到A → 再次回到B。

**不能用“同Root只能一次”同时代替这三种规则。**

因此，我建议撤下此前那条过宽的全局默认，改成：

> **监听去重、触发次数预算、反馈循环保护分别配置；已确认的多次触发不受新默认规则削减。**

同样，“检测祖先Effect”也不能被描述成已经解决所有无限循环。临时生成新实例、复制效果、延迟回调、充能转移，都可能改变实例身份或执行时刻。正式配置还需要检查这些跨效果连接；技术上的异常保护应记录错误，而不是悄悄吞掉正常效果。

现行文档本来就保留了“同一链暂不加总次数上限，但不开放禁用来源”的边界，词典不能另行引入一个未经确认的全局连锁次数上限。

## M04还要补一张“触发机会处理表”

达到门槛以后，应明确记录：

> 产生几次机会 → 本次执行几次 → 哪些暂存 → 哪些作废，以及原因。

“没有目标”“资源不足”“内置CD未好”“器具被控制”，不能全部混成同一种失败。

已定机制继续沿用其专门处理。例如【风过无尘】没有带CD目标时暂存机会，后来有目标就立即兑现；这不是所有物品共同的默认规则。

窗口计数也还需要明确是“从第一次事件起算的固定窗口”，还是“持续检查最近N秒的滚动窗口”。两者都可以表达，但不能让同一个词暗含两种算法。

# 四、M05：有两处明确笔误，以及几项需要补齐的空间规则

## 1. 左右方向写反了

第二批的例子：

> “法器放在火属性武器右侧，强化该武器。”

我后面写成了“选择法器右侧邻接目标”，这是错误的。

正确关系是：

```text
武器 W　法器 F
```

以法器F为来源，应选择**左邻接武器W**。

反过来，法器位于武器左侧时，以法器为来源，应选择右邻接武器。第五批的相似例子也需要按同一原则修正。

这类错误不会推翻空间框架，但必须从示例里清掉，否则Codex照着例子实现就会反。

## 2. 尺寸表达必须统一

按我们一直使用的“列数×行数”：

> **1×2是1列2行，纵向；2×1才是横向。**

前文把“1×2横向器具”写进例子，也应直接纠正。

## 3. 补充四个空间边界

| 边界         | 建议写法                                   |
| ---------- | -------------------------------------- |
| **是否包含自身** | “同行器具”“范围内器具”必须明确是否包含来源本身              |
| **多个区域重叠** | 同一效果同时覆盖同行、同列时，默认先按目标实例去重；按区域重复收益须明确写出 |
| **方向与旋转**  | “本盘右侧”和“器具自身朝向的右侧”不是一回事；现阶段优先使用本盘坐标    |
| **动态关系更新** | 只有关系真正建立／断开才产生事件，不能每次重新计算布局都重复触发“进入邻接” |

“中心”“边缘”“同行”还要保持两种判定的区别：**接触该区域**，还是**完全处在该区域**。不能在不同物品里悄悄换口径。

---

# 五、M06：效果库需要去重，而且一个恢复案例选错了目标

## 1. 不能给同一个动作建立多套独立实现

现在存在一些重复入口：

> C06与I12都修改护盾吸收率；
> D09与I10都修改状态容量；
> B07与I13都涉及资源上限；
> F04与H12都涉及器具冻结。

分类检索可以重复，但**底层行为必须只有一个权威定义**。

建议每个条目增加：

> **原子行为／复合模板／分类索引／预留扩展。**

例如“器具冻结”可以是复合模板，引用“暂停指定计时器＋禁止指定发动行为”，而不是在F类、H类各实现一套稍有不同的冻结。

“状态作为成本”也应由M08发起，调用统一的状态扣除行为；不能M08扣一次、M06又执行一次“消耗状态”。

## 2. 护甲恢复不能默认作用于每件器具

第五批有一句：

> “领域内己方器具每3秒恢复5护甲。”

这句话把阵盘空间目标与承伤资源目标混在了一起。现有护甲结算描述的是装备提供基准、战斗中记录当前护甲，战后清理本场值、下场按装备基准重建；不能据此自动给每把武器、每件法器各创建一个护甲池。

可以改成两种明确设计中的一种：

> **领域每3秒为持有者恢复5护甲，邻接防具数量影响恢复量。**

或者：

> **领域内每件合格防具分别触发一次回甲，恢复都落到持有者的护甲上。**

两者收益不同，不能混写。这里是修正目标对象，不是擅自选择第二种更强的效果。

同理，“护甲归零后恢复30”和“新建一个额外独立防御池”也不应混同。**从0恢复护甲本身不必另建一套重建系统。**

## 3. M06漏了对M04积累器的直接操作入口

我们已经定义了充能、阶段值、记忆，但效果库里没有完整列出：

> 增加／扣除充能；设置／清空计数；修改充能上限；写入／清除事件记忆。

这些应补进现有M06，并统一调用M04，不需要另开模块。否则“相邻法器获得1充能”仍然只能藏在自然语言里。

# 六、状态接口：要修正“驱散”同名，以及层数与时间状态的混用

## 1. 风系【驱散】状态，不等于立即驱散动作

这是一个必须明确的术语冲突。

现有【清风涤尘】是命中后施加【驱散】层数，再由该状态按自己的时钟拆除增益；不是命中瞬间直接拆掉同样数量的Buff。

所以词典应分别使用：

> **施加【驱散】状态**：状态操作。
> **立即移除目标增益**：即时驱散行为。

玩家文案可以保持自然，但数据ID和执行行为不能共用。

## 2. 不能把所有状态都写成“层”

前文“5层寒霜转换成2层虚弱”不成立，因为我们还没有决定虚弱采用层数制。

较准确的候选表达应是：

> 消耗指定数量寒霜，施加一次具有明确幅度和持续时间的虚弱。

“虚弱降低20%、持续5秒”目前仍是你举出的设计示例，不应被词典自动扩展成所有虚弱效果的正式基值。

状态操作必须先识别目标采用什么结构：

> **层数状态、限时效果、独立效果实例，或器具专属标记。**

另外，持续药效与免疫作为独立效果整体计一个驱散单位，这一点已有明确规则，不应再笼统放回“所有单位以后再定”。

---

# 七、M07：控制、计时和战后清理需要更严格的边界

## 1. 冻结暂停的不是全部时钟

假设某器具被冻结2秒。

它的轮转CD可能暂停，但**“冻结还剩多久”的计时不能也被自己暂停**，否则永远不能解冻。

因此要区分：

> 游戏／战斗时间是否推进；
> 某个器具的CD是否推进；
> 某个蓄势是否推进；
> 控制效果自身是否到期。

“冻结器具”必须指明阻止哪些行为、暂停哪些计时器，而不是一个笼统的 `paused=true`。

## 2. 多个阻止效果必须分别移除

例如器具同时受到：

> 2秒冻结＋5秒禁用。

2秒后只能解除冻结这一项，不能把器具直接设为“恢复正常”。是否能发动仍要检查剩余禁用。

这里建议采用“每个来源各有一份阻止记录”的表达，而不是一个总开关。

## 3. 既有同刻顺序必须写进词典引用，而不能继续泛写“以后定”

现在已经确认的包括：

| 同刻情形         | 已定处理           |
| ------------ | -------------- |
| 流血／灼烧刷新      | 保留原下一跳，不重排跳伤节奏 |
| 流血／灼烧到期与跳伤同刻 | 先移除，不结算到期末跳    |
| 麻痹到期与CD归零同刻  | 先解除麻痹，再检查本轮发动  |
| 连携后续恰好赶上窗口端点 | 仍然合格           |

前两类时间规则及麻痹边界已经明确；连携包含端点也已有单独确认。 

这不代表所有同刻事件都有统一答案。比如“同刻重新施加控制”和“同刻两方抢占资源”的复杂组合，仍需具体处理，不能用一条固定扫描顺序覆盖全部。

## 4. 战内离阵不能覆盖已定计数保留

前文把“离阵清空计数”列成了一个通用可选项，容易让人以为可以重新选择已有计数能力的生命周期。

现有确认是：**相关计数能力在战内状态归零、移出阵盘时不重置，战后重置。**这一点应直接保留；新器具另有特殊生命周期，才单独声明。

战斗结束时还应区分“正常到期”与“战后清理”。否则一个“Buff结束时爆炸”的器具，可能因为系统统一清理状态而在结算界面继续爆炸。

建议将结束原因记录为：自然到期、主动消耗、净化／驱散、替换、来源失效、战斗清理等，由具体效果选择监听哪些原因。

# 八、M08：完整支付还不够，必须补“整组支付一次完成”

之前写了“付得起所有必要成本才发动”，但没有把多个事件同时争用资源的情况说清楚。

例如角色只有8灵力，两件法器同刻各需要6灵力：

> 不能两件都先检查到“8≥6”，然后都发动，最后扣成负数。

建议把一次发动的处理明确为：

> **核定本次费用 → 检查整组必要成本 → 一次性完成扣付或预留 → 再发布实际发动事件。**

如果整组支付失败，不能已经扣了符箓、没扣成灵力，却仍发出“成功发动”的通知，除非某个具体能力明确采用分段付款。

还需要补三处：

**退款与恢复分开。**退回发动费用不应自动当作治疗、回灵效果，否则退款可能触发额外回灵构筑。

**预留与免疫资源损失分开。**预留灵力只是限制己方其他消费，不能自动变成敌方枯脉无法扣除的安全仓库。敌方扣资源后预留如何调整，是使用这类机制时需要明确的细节。

**费用公式引用既有规则，不引入万能计算顺序。**前文“基础→固定值→百分比→独立乘区→设值”的通用排列应降为待选模板，不能覆盖既定伤害、费用、恢复和时间算法。

尤其现有镇脉诀、重伤、御兵术、百兵归元各有费用边界，不能因为进入M08，就被简化成一条新公式。

---

# 九、M09：不能让“强制”与“配置优先”绕开已有规则

这里有两项需要收紧。

## 1. CD归零、强制就绪，不等于无条件发动

前文把“CD推进、立即归零、强制就绪、额外发动”分开是有价值的，但它们不能成为绕规则的不同名字。

已经明确：

> 减CD效果不作用于带减CD能力的器具／法术；已就绪目标不能继续推进；冻结期间风系CD干预不能触发。

因此，前文那个：

> “监听寒霜成功冻结后，立即缩短邻接武器CD”

不能直接作为合法案例，因为它可能正好踩到冻结期间的禁止条件。应更换例子，或等待具体机制对时间节点作明确设计，而不是凭“监听法器”取得默认豁免。

同样，“直接归零”不能只因换了一个行为名称，就避开减CD目标资格。额外调用武器也仍须检查入阵、控制和费用等已有门槛。

## 2. “配置优先”要改成“经过确认的专门规则优先”

上一版总则写：

> 配置优先，默认规则兜底。

作为数据读取方式可以理解，但作为设计原则过宽。否则任意物品配置都能写：

> 可暴击、可引雷、无视冻结、无限连携。

较准确的规则应是：

> **先遵守当前已确认规则；具体物品只有通过明确设计确认，才能成为一项有边界的例外。配置负责记录这个例外，不负责自行创造许可。**

尤其修改攻击来源、增加属性标签，不能自动获得全部关联资格。**拥有雷属性识别标签，不等于实际造成了正数雷伤；拥有父事件，也不等于失去武器攻击资格。**

这两条应一起写进M03、M06、M09的衔接说明。

# 十、M10：来源管理存在一处与定案不符，以及一个身份混淆

## 1. “公共状态默认不记逐层来源”不能一概而论

枯脉确实已经明确为统一状态池，不按逐层来源分账；但不能据此推广到所有公共状态。

《清风涤尘·洗尘》只强化由本术施加的驱散，文档明确要求保留来源归属，混合来源的精确分账仍留给完整流水线。

普通灵障也已有来源受限的用途：返锋只使用兵甲化元生成、尚未消耗的那一部分灵障，不能使用其他来源的盾值。

所以应当改成：

> **是否统一显示、是否统一运行、是否需要来源账目，是三个独立问题。**

一个界面上只显示一个总池，后台仍可能需要记录部分来源份额。

M10应支持但不强迫每种状态采用：

> 不分来源、记录参与者、记录来源份额、记录逐层／逐批来源。

具体使用哪一种，由该状态已有规则或专项确认决定。

## 2. Origin前后定义不一致

前文一处把Origin解释为“最初开启整条事件链的武器”，另一处又把火球Origin解释为“创造火球能力的法器”。

这应拆开：

> **因果起点**：这条链最初由哪次行动引起。
> **能力来源**：这份效果是哪件器具的哪个能力产生。
> **当前控制者**：现在谁控制它。
> **结果归属**：伤害／统计记到谁名下。

不再让一个Origin字段同时承担两种含义。

复制、窃取、反射还要保留旧事件的因果记录。**创建新实例不能顺便洗掉递归限制、刷新每战一次次数，或把已支付的效果重新变成免费完整使用次数。**

另外，`UniqueGlobal`也要说明作用范围：每个角色唯一、每个目标唯一、每场战斗唯一，还是套件内唯一。不能含糊成“整个游戏世界只允许一份”。

# 十一、跨模块终审还发现三项“不能靠词典自动解决”的衔接问题

## 1. 凡人可以使用凡品，但不意味着凡品施加状态一定能生效

你已经明确凡品开始可以有属性伤害、Buff或Debuff能力；而现行核心状态容量规定，凡人基础容量为0，可由合格额外容量开启实际持有。

因此第一批凡人装备不能只设计：

> 命中后获得1附炎。

还必须检查：**相关角色的附炎最终容量是否大于0。**

这不是要推翻凡品设计，而是说明容量来源要跟着第一批状态装备一起设计。至于容量由阵盘、法器还是某件器具的明确效果提供，需要落实，不能默认为“凡品自动附赠”。

## 2. 玄品能够修改连携规则，不等于提前开放所有连携

“某品级允许设计什么机制”与“角色境界是否解锁该机制”是两个条件。

现行共鸣从元婴开启；器具参与连携仍有化神门槛。不能因为元婴可以使用玄品，就默认该玄品立即开放全部器具连携。

装备可以有分阶段生效的能力，也可以以后设计明确例外，但这需要物品自己的规则。

## 3. 实练修为是新增路径，不能只当成资源日志

你提出的稻草人实练方向已经很清楚：在合格修炼场景中，通过真实轮转与资源消耗训练。

这对旧文档“非战斗功法修为必须由特定法器提供”的条款，确实属于需要正式记录的补充／修订，而不只是换一种描述。

词典可以提供训练事件、支付记录和结果归属，但仍要把以下内容留给T03：

> 训练收益加到哪种进度；哪些动作合格；被打断、退款、复制攻击是否计入；不同训练目标与器具怎样影响收益。

**不能直接从“Credit归玩家”推导出“玩家所有功法都获得经验”。**战斗功法经验仍有原书上阵、胜利和境界门槛等自己的规则。

# 十二、哪些扩展应保留，但不能写成“已经决定做”

前几批为了避免遗漏，我加入了控制权夺取、永久器具销毁、位置交换、临时占格、复苏、复制上一效果、信息揭示等方向。

这些可以留在资产库，但应标明状态：

| 状态        | 含义                   |
| --------- | -------------------- |
| **已定机制**  | 已有明确规则，词典负责准确表达      |
| **建议默认**  | 适合新物品采用，但不能覆盖已定特例    |
| **预留扩展**  | 能表达这种能力，不等于已经决定制作    |
| **待专项确认** | 需要状态、法器、成长或完整流水线专题补齐 |

尤其敌方阵盘本来就以可见、可针对为重要方向。**不能为了给“侦测法器”制造用途，反过来把原本应公开的信息隐藏。**

同理，普通器具失效、战内禁用与永久删除玩家库存，不应共用一个模糊的“销毁”。

# 十三、这轮反向核对后的结果

下面是文本规则核对，不是运行游戏后的测试结果。

| 反向案例                | 本轮发现／修正                |
| ------------------- | ---------------------- |
| 法器在武器右侧，强化那把武器      | 修正为从法器选择左邻接目标          |
| 一次武器发动同时发出器具事件与攻击事件 | 关联同一行动，防止监听重复计数        |
| 御兵术调用武器攻击           | 不因有父事件就改成普通派生伤害        |
| 一次驱散12层、每5层一次机会     | 保留两次机会，不被同Root一次规则吞掉   |
| 一击破多层雷盾             | 按已定破层事件处理，不被通用去重合并     |
| 连携追加包紧接B本体          | 保留同轮身份，不错误启用灵障或提前生新盾   |
| 两种控制先后到期            | 分别解除，不因一个到期而清掉全部控制     |
| 两件器具同刻争用8灵力，各需6     | 支付必须按规则先后完成，不能都成功      |
| 满血时发生治疗尝试           | 不等于没有治疗事件，仍检查已有重伤分支    |
| 公共驱散池混有洗尘来源         | 保留必要来源账目，不一律抹除         |
| 领域为邻接防具提供回甲能力       | 明确恢复对象及计次，不能给每件器具私建护甲池 |
| 凡人使用施加核心状态的凡品       | 必须检查额外容量来源             |
| 复制、移出再入阵、延迟回调       | 不得借新实例或新回调重置受限次数和因果限制  |

## 最终结论

**M01～M10不需要推倒重做，也不需要增加M11。需要做的是一次“规则收束”，而不是继续扩张机制数量。**

本轮最关键的修正有四个：

**把发动方式拆成可组合维度；把因果来源与战斗身份分开；把事件去重、触发次数与防递归分开；按具体状态保留必要的来源账目。**

同时清除方向、尺寸、护甲目标等明确错误，把已定时间／控制规则嵌回对应模块，并将预留机制从正式规则中分出来。

所以，当前版本更适合叫 **《T01机制词典 v1.0审校稿》**。完整事件组合与实际验证仍需要后续T08接续，路线图也明确把流程审定与实现／模拟分成两个阶段。

**下一步应先把这份修正单合并回十个模块，形成一份没有重复定义和相互冲突的统一正文，再进入状态词典。**这样后面使用的就不再是五批散稿，而是一份能作为物品设计依据的版本。
