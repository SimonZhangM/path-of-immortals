# 《苍澜界》阵盘战斗复盘系统｜Codex 实施规格 v1.0

> 文档用途：交给 Codex，在**现有 Godot 项目中**落实战后阵盘统计覆盖层与“复盘专用悬浮详情”。
>
> 重要：以下为**功能与数据契约**，并非声称项目中已经有指定节点、脚本或字段。先勘查项目，复用已有战斗结算、阵盘、物品悬浮及战斗记录系统，再按实际工程命名落地。不要额外重做战斗场景、物品库或结算规则。

## 0. 最终任务（不可偏离）

1. 在现有战斗结束画面进入“战斗复盘”模式：保留我方/敌方阵盘、物品图片、格位和战场背景，在每件物品的图标**内部下方**叠加本场统计简条。
2. 普通类型最多 **3 条**，恢复型最多 **4 条**。数据顺序为“主要贡献 → 次要贡献/实际消耗 → …… → **转轮次数**”，凡显示转轮次数，**必须是最后一条**；无转轮机制不伪造转轮。
3. 鼠标移到某件物品时，**原物品属性说明整块替换为该物品的“战斗统计详情”**，不是在旧悬浮上再叠一层。鼠标离开隐藏，退出复盘恢复原悬浮。
4. 双方相同规则；同名不同实例分开统计；占多个格位的物品只叠一份数据并只弹一个悬浮。
5. 所有数值来自结算事件/冻结快照；不得通过解析战斗记录的中文文本、面板文本、差分敌人最终血量来猜数。
6. **只做战后复盘 UI 和必要事件埋点**，不改变原本战斗数值、CD、Buff/Debuff、胜负判定、物品属性说明内容。

---

## 1. 先检查项目（Codex 的第一步）

- 识别 Godot 具体版本及 GDScript/C# 使用情况，勿假定为某个版本。以下 Godot API 建议以 Godot 4.x 为参考；若项目版本不同，按项目适配。
- 找出现有：战斗结束场景、双方阵盘显示组件、物品/法术统一卡格组件、原物品悬浮组件/悬浮路由、战斗结算事件或战斗记录数据源、切换统计模式按钮、返回战场/关闭逻辑。
- 识别已有物品唯一实例 ID、角色阵营、物品占格、主动轮转与被动触发、气血/体力/灵力、护甲/护盾、状态来源等结构。已有数据优先复用，避免再建一套平行的战斗事实来源。
- 先输出短勘查清单：现有文件/节点路径、可复用接口、缺失的数据字段、预计改动文件。随后直接实施，无须等待用户重新确认已有要求。

## 2. 模式与用户流程

### 2.1 模式状态

- `NORMAL`: 原战斗或常规物品界面；物品仍显示原属性悬浮；无复盘简条。
- `REPLAY`: 战斗结束后选“战斗复盘/切换统计模式”进入；显示双方统计简条；物品悬浮由复盘专用统计**完全取代**原物品悬浮。
- 用户关闭复盘或离开战斗结果画面时，销毁/隐藏复盘层，恢复 `NORMAL` 的悬浮路由与鼠标行为；不得残留复盘数据到下场战斗。
- 复盘数据是本次战斗**结束时冻结的只读快照**；切换「总览/伤害/恢复/防护/触发」仅改变简条显示，不重新计算数据、不影响战斗状态。

### 2.2 显示与交互

- 原场景元素（胜/负结果、战斗用时、双方头像、双方阵盘、背景与按钮）保留，按现有结构添加覆盖层，不复制一套阵盘来假装复盘。
- 每件物品默认显示简条：半透明深色底，左小图标、右简短数字；保持图标原美术可辨认。**显示顺序按列表自然向下，转轮永远排最后。**
- 2～3 项使用纵向排列；恢复类四项优先四行紧凑排列，若单格高度不足，采用 2×2 紧凑网格，但阅读顺序依然是前 3 项、**第 4 项转轮**（右下），不删掉第 4 项。
- 单格、多格以物品占用矩形为定位基准；放在物品图片下缘或占格矩形下缘，不因跨格生成两份。
- 阵盘空格和没有归属的纯装饰物不显示任何数据；双方都应支持。
- 当前筛选按钮可改变简条的关注内容，但**悬浮仍展示该物品完整、相关的本场统计**，不把悬浮也缩减成筛选单项。

## 3. 阵盘简条：按物品主要用途配置模板

> 分类优先读取物品/效果配置中的 `replay_profile`，不要根据战后数值大小临时更换主指标，以免同一物品每场显示项跳来跳去。`rotation_count` 在任何包含它的模板里必须 `append` 到**末尾**。空项不占位置。

| 预设用途 | 主要项（固定优先） | 第 2/3 项的选择 | 转轮 | 最多 |
|---|---|---|---|---|
| 武器、攻击法器、攻击法术 | `累计真实伤害` | 主消耗资源（耗体/耗灵，按物品配置） | 最后 | 3 |
| 主要补护甲的装备/法器 | `实际提供护甲` | 优先显示本场实际消耗；无消耗且确能生盾时，显示实际生成护盾 | 最后（有转轮才显示） | 3 |
| 主要生护盾的装备/法器 | `实际生成护盾` | 优先显示实际消耗；无消耗且确能补甲时，显示实际提供护甲 | 最后（有转轮才显示） | 3 |
| 专门提供攻击 Buff 的法器 | 可可靠归因则 `增伤贡献`；否则 `增益施加次数` | 实际消耗；无消耗且有触发时显示`有效触发次数` | 最后 | 3 |
| 专门提供防御 Buff 的法器 | 可可靠归因则 `减伤贡献`/`护盾承伤`；否则 `增益施加次数` | 同上 | 最后 | 3 |
| 伤害型 Debuff 法器（毒蚀等） | `该物品实际累计伤害`（直接伤害+归属明确的状态独立伤害） | 实际消耗；无消耗可显示状态生效/触发次数 | 最后 | 3 |
| 控制/削弱型 Debuff 法器 | `减益施加次数`，或项目已有明确且可靠的量化贡献 | 实际消耗；无消耗可显示冻结/麻痹/追击等触发次数 | 最后 | 3 |
| 纯被动装备/状态 | 归属明确的实际贡献 | 存在则显示第二种可归属贡献 | **不伪造转轮**；若有被动触发，可将触发次数放最后 | 3 |
| 以恢复为主要用途的物品/法器/法术 | `实际恢复气血`、`实际恢复体力`、`实际恢复灵力` 中本场大于 0 的项（按此顺序） | 恢复类简条**不显示消耗**，消耗进悬浮详情 | **永远最后** | 4 |

### 3.1 特殊和边界

- **恢复类**：只恢复气血→`气血+56 / 转轮4`；三种都恢复→`气血+56 / 体力+20 / 灵力+12 / 转轮4`；实际全是零→仅显示`转轮4`（若有转轮）。零值恢复不占位。
- **攻击类**：物品实际发动过却全部未命中，`伤害0`仍显示，方便诊断；凡不能可靠归属的辅助数值，显示可验证的施加次数，不得把“不知道”写成`0`。
- **双资源消耗**：普通物品主图只有一个消耗位，优先物品配置的主消耗；若主消耗实际为0而另一资源实扣大于0，可改显示另一种实际消耗；完整的两种实际消耗均显示在悬浮。
- **攻击附带吸血/回灵、护甲偶尔上 Buff**：维持原主要用途模板，额外效果在悬浮详情中显示；不因为这场伤害小、治疗多，就把武器改成恢复类。
- **护甲与护盾同给**：有实际消耗则优先“主防护贡献+消耗+转轮”；无消耗可显示“护甲+护盾+转轮”。其他 Buff 统计放悬浮。
- **转轮 0**：物品具备主动轮转能力却一次没发动，显示`转轮0`；没有转轮机制则不显示转轮。被动“触发次数”不能冒充“转轮次数”。
- **一次发动多段、多目标**：转轮仅+1；伤害将各次实际命中/扣除加总；独立的后续伤害触发不额外加转轮。
- **0 与无数据区分**：明确执行但无效果是数值0；从未捕获到归属/数据缺失是`不可统计`（详情中说明），绝不伪装为0。

### 3.2 例子（仅示意）

```
赤焰刀         [伤害 1240] [体力 -32] [转轮 8]
护甲护臂       [护甲 +80]  [护盾 +30] [转轮 5]
振气法器       [增伤贡献 +85] [灵力 -24] [转轮 5]
破甲法器       [减益施加 4次] [灵力 -20] [转轮 6]
三系恢复玉佩   [气血 +56] [体力 +20] [灵力 +12] [转轮 4]
未发动长剑     [伤害 0] [转轮 0]
```

## 4. 悬浮详情：必须替换原属性悬浮

### 4.1 悬浮状态路由（关键）

1. 鼠标进入物品有效占格范围，先判断 `current_mode`。
2. `NORMAL` → 继续调用现有 `ItemTooltip`/原悬浮逻辑，不做任何功能删改。
3. `REPLAY` → **禁止显示原悬浮的属性/品质/价格/装备基础说明/炼化描述等原版正文**，改调用 `BattleReplayTooltip` 读取该 `item_instance_id` 的本场快照。
4. 进入复盘时若原悬浮正打开，立即关闭并以当前物品实例刷新复盘悬浮；退出复盘时关闭复盘悬浮，正常路由恢复。
5. 悬浮只是“数据详情”，可以保留物品图标、名称及类别以识别物品，但不得在其下重复原物品属性表。
6. 悬浮内容不依赖简条模式：阵盘当前切到“伤害”时，悬浮仍能查看所有属于该物品的有效恢复、消耗、防护和状态贡献。

### 4.2 悬浮内容（自上而下）

```
┌─ 物品图标 + 名称（类型 · 本场战斗统计） ─────────┐
│  核心统计（与该物品阵盘简条同源；2-4个小块）       │
├─────────────────────────────────────────────────┤
│  效果构成（按物品实际功能动态显示）                │
│  直接伤害 / 状态独立伤害 / 反击伤害等              │
│  施加增益/减益次数、叠层或刷新、有效触发次数       │
│  护甲实际提供量、护盾实际生成量、护盾实际承伤       │
│  可可靠归因的增伤贡献、减伤贡献（明确标注辅助贡献）│
│  恢复气血、体力、灵力（实际恢复）                  │
├─────────────────────────────────────────────────┤
│  发动表现                                         │
│  转轮次数；主动发动次数；命中/未命中/暴击（适用时） │
│  实际消耗体力、灵力；每次发动平均实际伤害（可选）  │
└─────────────────────────────────────────────────┘
```

- **显示全量相关指标，不强制填满无关栏目**：武器不显示从未具备的治疗功能；纯防具不显示暴击。核心有0值且该物品执行过该功能，保留0以便排查。
- 常规建议 6～10 条明细；某物品实际效果很多时，详情内部滚动或增加折叠分区，不能截断数据、不能撑出屏幕。无关分区不生成。
- `平均每次发动伤害 = 总真实伤害 / 实际发动次数`，当发动次数为0时显示`—`而不是除零；多段攻击需明确“命中次数”按命中结算笔数统计，不等同转轮次数。
- 如果增伤/减伤归因无法精确得出，不显示虚构数字；可显示 `增益施加 4次 / 有效触发 9次 / 增伤贡献：未单独归因`。
- 本场实际消耗体力和灵力在悬浮中**分别**显示，不能用净值抵扣同场的资源恢复。
- 鼠标短暂停留后出现，离开物品后消失；悬浮框定位优先相邻空白区，靠屏幕边缘自动翻向和限制坐标，不能超出画面。
- 当前阶段以**只读悬浮**为核心交付；“查看相关记录”若项目已有稳定的可点击悬浮路由，可选对接按 `item_instance_id` 筛选的原战斗记录。不要为了悬浮上的按钮而破坏鼠标离开/捕获逻辑。也可采用点击物品再查看记录的后续扩展。

### 4.3 三种悬浮示例

**武器**：`赤焰刀` → 核心 `总伤害1240 / 耗体32 / 转轮8`；构成 `直接1100 + 毒蚀140`；发动 `8次 / 命中6笔 / 未命中2笔 / 暴击2笔`；均伤`155`。

**纯增益法器**：`振气法器` → 核心 `增伤贡献85 / 耗灵24 / 转轮5`；明细 `振气成功施加4次 / 参与攻击9次 / 可可靠归因增伤85`；其贡献不是额外真实伤害，不参与全场伤害再求和。

**护甲装备**：`玄甲护臂` → 核心 `提供护甲80 / 生成护盾30 / 转轮5`；明细 `实际护甲补入80 / 护盾净生成30 / 护盾承伤18 / 附加增益施加2次`；共享护甲池的承伤不虚构分摊给该件装备。

## 5. 数据契约：战斗结算事件而非日志文本

### 5.1 每件物品必须有稳定身份

- `battle_id`：本场战斗唯一键。
- `actor_id` 和 `side`：物品所属角色与阵营（我方/敌方）。
- `item_instance_id`：**唯一实例键**，同名两把剑不同 ID；一件占多个格子仍只有一个 ID。
- `item_definition_id`：物品配置键，用于取显示名称、图标、`replay_profile`，不能用于合并两件同名物品。
- `occupied_cells` 或绑定组件的 `Rect2`：多格占用范围，用于定位简条和悬浮，不用于统计次数。
- `activation_id`：每次真实发动唯一键，同一发动的扣资源、多段伤害、施加状态共享它，避免多次转轮。
- `event_id`：每条结算事件唯一键；汇总时去重，避免信号重复或战斗回放触发二次统计。
- `effect_instance_id`：状态/护盾/反伤等效果实例唯一键；保存`origin_item_instance_id`，让后续跳伤、承伤、触发能够追溯。

### 5.2 建议统一事件类别（可映射已有结构）

| 事件 | 关键量 | 归属 |
|---|---|---|
| `ACTIVATION_COMMITTED` | `activation_id` | 实际发动的物品；每个ID仅计一次转轮 |
| `RESOURCE_COST` | `resource = stamina / mana`，`actual_amount` | 实际扣资源的物品；不可用理论耗量代替 |
| `DAMAGE_APPLIED` | `actual_shield_loss`、`actual_armor_loss`、`actual_hp_loss`、`kind` | 本次**独立伤害**真实来源；合计三类实际扣除值 |
| `HEAL_APPLIED` | `resource = hp / stamina / mana`，`actual_restored` | 造成本次恢复的物品或状态来源 |
| `ARMOR_GRANTED` | `actual_added` | 实际补入共享护甲池的物品 |
| `SHIELD_CREATED` | `effect_instance_id`、`actual_added` | 净增加盾值的来源；续盾仅计实际增加量 |
| `SHIELD_ABSORBED` | `effect_instance_id`、`actual_absorbed` | 提供该盾的来源；用于护盾承伤统计 |
| `STATUS_APPLIED` | `status_id`、`is_buff`、`successful`、`change_type` | 原施加来源；成功叠层/刷新按一次成功施加计 |
| `STATUS_TRIGGERED` | `effect_instance_id`、`trigger_id` | 状态的原施加来源；触发次数去重 |
| `DAMAGE_ASSIST` | `actual_increment`、`reason`、`reliably_attributed` | 攻击 Buff / 防御削弱的**辅助贡献**；不再次计真实伤害 |
| `DAMAGE_MITIGATED` | `actual_prevented`、`reliably_attributed` | 减伤 Buff 原来源；不可把护盾承伤冒充减伤 |
| `PASSIVE_TRIGGERED` | `trigger_id` | 被动物品；不是主动转轮 |
| `HIT_RESOLVED` | `hit / miss / critical`、`target_id` | 用于悬浮的命中/未命中/暴击笔数，独立于转轮次数 |

### 5.3 示例数据结构（字段名可按已有工程映射）

```json

  "item_instance_id": "weapon_A_001",
  "item_definition_id": "flame_blade",
  "actor_id": "player_1",
  "side": "ally",
  "replay_profile": "ATTACK",
  "is_rotating": true,
  "metrics": {
    "damage_direct": 1100,
    "damage_status_independent": 140,
    "damage_total": 1240,
    "stamina_spent": 32,
    "mana_spent": 0,
    "rotation_count": 8,
    "hit_count": 6,
    "miss_count": 2,
    "crit_count": 2,
    "hp_restored": 0,
    "stamina_restored": 0,
    "mana_restored": 0,
    "armor_granted": 0,
    "shield_generated": 0,
```

## 6. 计算与归属：必须一致

1. **实际伤害**：事件的`护盾实际扣除 + 护甲实际扣除 + 气血实际扣除`。按实际结算封顶，过量伤害不计；相同伤害结算不能既归武器又归Buff法器。
2. **毒蚀等持续伤害**：由独立状态伤害事件实际扣除多少计多少；带 `effect_instance_id`回溯到施加该状态的具体物品。状态由多个来源叠层且结算是混合的，战斗核心应提供每个来源的份额；若当前不能可靠拆分，留“混合状态/未单独归属”，禁止全额记给最后施加者。
3. **加攻Buff/破甲增伤**：武器保留实际完整伤害，Buff/Debuff法器只取得经核心可靠计算的`damage_assist`。此值是**辅助贡献**，不再加到全场真实伤害。属性加成乘算、暴击、护甲绕过、交互分摊不在UI侧重算。
4. **Buff独立雷击/反伤**：如确实额外生成一个伤害结算，伤害归该 Buff/反伤来源物品，其实际伤害计入全场真实伤害一次；引发触发的普通攻击不重复记此部分。
5. **减伤**：减伤效果真正避免的伤害记到原来源 `damage_mitigated`，不包括后来由盾/护甲接住的伤害。多减伤交互由核心提供可验证归因；不能归因时以成功施加/触发次数替代。
6. **护甲**：只统计该件装备实际补入/提供的护甲（含有明确来源的开战初始授予），不将共享护甲池的全场承伤随意按装备平摊。仅提高护甲上限、但未实际补入护甲值时，不虚增“提供护甲”。
7. **护盾**：生成量按净增加计算；旧盾10→30计+20，仅续时计+0。各独立护盾有实例来源；真正扣掉的盾量计入对应来源的`shield_absorbed`。不要把盾承伤再次加进“减伤”或“护盾生成”。
8. **恢复**：气血/体力/灵力分别按实际恢复值累计，溢出不计。恢复法器发动却资源满，恢复显示0并按恢复模板隐藏零值行，仍保留转轮。
9. **消耗**：分别累加实际体力消耗、灵力消耗；不能与同场恢复相抵。未完成发动时的尝试是否花费资源，按真实扣除事件统计；`rotation_count`只统计真正`ACTIVATION_COMMITTED`，不按读秒结束累计。
10. **状态次数**：每个目标、每种状态、每次成功施加/叠层/刷新计1次；同一事务中叠3层不计3次；免疫/抵抗/无变化不增加成功次数；状态自然到期/普通消层不额外增加次数。多目标逐目标统计。
11. **转轮/被动**：主动转轮只由发动ID统计；被动触发以独立触发ID统计。启动时CD满不代表自动+1，DoT跳伤/追击若未经过物品自己的轮转，则不增加原物品转轮。
12. **无物品直接造成伤害**：角色本能、无对应阵盘物品的技能或场景效果保留独立来源，不能为了让物品伤害合计对上而强行分摊。

## 7. UI节点组织建议（示例，非既有路径）

```
BattleResultScreen (原节点；复用)
├─ AllyBoard (原双方阵盘组件)
│  └─ ItemCell(s) (原物品命中区域)
├─ EnemyBoard
├─ ResultControls (原返回/复盘/战斗记录按钮)
└─ ReplayUILayer (新增，复用原阵盘坐标)
   ├─ ReplayStatOverlayHost (一件物品一组简条；mouse_filter=IGNORE)
   └─ ReplayTooltipHost (唯一可见复盘悬浮)

BattleReplayController (状态/模式、冻结快照、显示筛选)
BattleReplayCollector (把战斗结算事件聚合成每物品统计)
BattleReplayFormatter (按replay_profile生成有序简条与详情行)
```

**节点原则：** 如果项目已有统一物品 tooltip manager、battle log manager、UI CanvasLayer，则扩展现成管理器；命名不必逐字照抄。不复制可交互阵盘节点、不引入第二套物品点击检测。

### 7.1 悬浮路由伪代码

```gdscript
# 示意；Codex 须结合项目实际信号/函数名实现。
func on_item_hover(item_instance_id: String, item_anchor: Control) -> void:
    if replay_controller.is_replay_mode():
        original_item_tooltip.hide() # 原物品属性悬浮不再出现
        replay_tooltip_host.show_stats(
            replay_controller.get_item_stats(item_instance_id),
            item_anchor.get_global_rect()
        )
    else:
        replay_tooltip_host.hide()
        original_item_tooltip.show_item(item_instance_id)

func on_item_leave() -> void:
    if replay_controller.is_replay_mode():
        replay_tooltip_host.hide()
    else:
        original_item_tooltip.hide()

func on_replay_exit() -> void:
    replay_tooltip_host.hide()
    replay_stat_overlay_host.clear()
    replay_controller.set_replay_mode(false)
    # 原悬浮路径和事件订阅恢复正常
```

- 覆盖层的所有非交互 `Control` 子节点设 `mouse_filter = Control.MOUSE_FILTER_IGNORE`，使鼠标仍落到原物品的 hover 区域；Godot 官方文档说明该属性会影响 `mouse_entered`/`mouse_exited` 与事件传递。
- 若已有 Godot 原生 `_make_custom_tooltip()`，可在既有悬浮适配器中依据模式返回复盘内容；但**别在原属性 Tooltip 和复盘 Tooltip 同时创建可见窗口**。有自绘 TooltipManager 的项目优先用原管理器路由。
- 悬浮框自身若只读，也设忽略鼠标，避免其遮住下层导致 hover 闪烁；若后续加入点击“相关记录”，需另设固定详情/点击路由，不直接依赖一个鼠标移开即销毁的普通 tooltip。

## 8. 图标/数值显示协议（13科目）

| ID | 用途 | 主图/悬浮 | 来源要求 |
|---|---|---|---|
| `damage` | 实际造成伤害 | 两者 | 交叉剑（红） |
| `heal_hp` | 恢复气血 | 两者 | 绿十字 |
| `stamina` | 体力正负变化 | 两者 | 原游戏体力图标，数值`+/-`区别恢复和消耗 |
| `mana` | 灵力正负变化 | 两者 | 原游戏蓝色灵力图标，数值`+/-` |
| `armor_grant` | 实际提供护甲 | 两者 | 白色甲衣 |
| `shield_create` | 生成护盾 | 两者 | 蓝盾 |
| `buff_apply` | 施加增益 | 两者 | 上行箭头 |
| `debuff_apply` | 施加减益 | 两者 | 下行箭头 |
| `rotation` | 转轮次数 | 两者，永远放最后 | 金色轮转双箭头/轮盘 |
| `damage_assist` | 增伤贡献 | 两者 | 剑+上行箭头，不能与纯伤害图标混淆 |
| `damage_mitigated` | 减伤贡献 | 两者 | 被截住的入射攻击 |
| `shield_absorbed` | 护盾承伤 | 悬浮为主 | 盾+撞击闪光 |
| `trigger` | 状态/被动触发次数 | 两者 | 四芒闪星，与转轮图标不同 |

- 优先复用项目现存图标与用户先前制作的13图标合集；若资源未导入，先在工程中明确记录缺失路径，允许用同尺寸占位，不编造资源路径。
- 所有图标统一简化、无额外复杂纹理；阵盘上以16～20px可读性为优先。伤害红、回血绿、护甲/护盾蓝、增益青、减益紫、转轮金；资源图标优先原游戏颜色。
- 数值规则：伤害/次数普通正数；恢复`+N`；消耗`-N`；增伤贡献可`+N`并配增益标识；末行转轮显示`N`或`N次`。保留内部真实精度，**仅展示时按项目统一数值舍入规则格式化**，不可先逐笔四舍五入再汇总。

## 9. 统计模式按钮

- `总览`：按第3节模板显示全部应显示的项目。
- `伤害`：显示该物品真实伤害；有明确辅助增伤的，可标为“辅助贡献”，但不要混入真实伤害的总和；无伤害类别弱化显示，非参与物品不强制显示`0`。
- `恢复`：分别显示实际气血/体力/灵力恢复的正值，恢复0隐藏。
- `防护`：显示实际提供护甲、净生成护盾、可靠归因减伤；详情保留护盾实际承伤。
- `触发`：显示触发/生效次数，主动物品的`转轮`也可作为运行次数显示，但**明确区分两个图标和含义**。
- 所有模式中，凡物品上**显示了转轮次数，它必须处在该物品简条最后**。筛选仅修改简条，悬浮始终可查本场全部相关统计。

| C. 同一发动打3目标，另造成2段追击 | 对出手物品转轮只+1；实际各目标各段独立伤害加总 |
| D. 两件同名武器在不同阵盘位置 | 各自显示不同实例统计，不互相合并 |
| E. 同一件2格身甲 | 只显示一次简条，任一占格悬浮同一份统计 |

| I. Buff无法可靠归因增伤量 | 主图回退为增益施加次数；Tooltip不写伪造的增伤0 |
| J. 毒蚀来自两件法器 | 每跳按来源实例精确归属；若缺乏来源份额，不把全部毒伤算给两件或最后施加者 |
| K. 盾剩10续到30 | 生成护盾只+20；只续时+0；护盾承伤单独统计 |
| L. 护甲共享池被打掉100 | 不把这100平分给各护甲物品；各自提供护甲仅按真实补入统计 |
| M. 一件装备仅被动减伤，无转轮 | 不显示`转轮0`；有效触发才显示`触发` |

| P. 退出复盘或关闭战果画面 | 统计覆盖层清理；原悬浮恢复；下场战斗不泄漏上场数据 |
| Q. 鼠标从左下阵盘快速切到右侧敌阵盘、靠屏幕边缘 | 悬浮随当前实例更新，不错位、不闪烁、不出屏；透明覆盖层不阻挡原物品 hover |
| R. 1366×768与1920×1080、1格/2格/4格占位 | 行数与最后转轮规则不变；图标/数字可读，悬浮不遮住鼠标目标区域 |

### 10.1 最终可核对的关系

- 对某件物品：`真实总伤害 = 直接伤害 + 状态独立伤害 + 独立反伤/追击等实际伤害`，每一笔真实伤害只能归属一次。
- `伤害辅助贡献`与`减伤贡献`是独立分析指标，**不加到真实伤害或真实承伤总和**。
- `真实战场总伤害 = 各归属明确物品伤害 + 不属于任何物品的角色/场景伤害 + 暂不可明确分配的状态伤害`。
- `转轮总次数`不等于命中笔数、状态触发笔数或CD读秒完成次数。
- 本场数据与既有战斗记录出自同一事件源；筛选或格式变动不改变统计结果。

## 11. Codex 分步交付顺序

**第一阶段｜接通真实数据**
1. 查现有战斗事件管线、结算点、物品实例 ID 和来源链；补必要事件字段与实例来源，不改变算法。
2. 增加/扩展`BattleReplayCollector`，按实例聚合并在战斗结束生成只读快照。
3. 使用小型固定事件样本验证总数、状态归属、转轮和防护统计。

**第二阶段｜阵盘覆盖**
4. 给现有双方阵盘复用组件加复盘数据覆盖层，处理多格占用矩形；按`replay_profile`统一格式化简条。
5. 接入模式按钮和五种显示筛选，保证任意显示转轮时必为最后一项；未进入复盘不能出现简条。

**第三阶段｜原悬浮的完全替换**
6. 在现有物品 hover 入口做`NORMAL/REPLAY`路由；复盘详情从冻结快照生成，不能出现旧物品属性正文。
7. 修正悬浮屏幕边界、Hover遮挡、鼠标跳转与关闭恢复；确认双方物品正常。

**第四阶段｜验证与交付**
8. 运行项目现有测试；若支持 Godot headless，执行项目版本适用的无头加载/脚本语法检查；对照表中测试用例验证。
9. 在 16:9 的战后场景进行最终视觉核查；把新增/修改的具体文件、数据埋点、使用的图标路径、测试通过情况和已知限制列入实施总结。
10. 如缺少13图标的素材原文件，可以临时使用现有同义资源或占位图，但务必标记待替换，不要因为缺素材阻塞核心统计与交互。
